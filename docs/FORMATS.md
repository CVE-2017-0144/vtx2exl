# Форматы

Для каждого формата: что читаем или пишем, на что именно опираемся и что увидишь, если формат поменяется. Проверять изменения удобнее всего сравнением файлов до и после действия в программе-источнике, см. `MAINTAINING.md`.

Пути ниже записаны так: `<игра>` папка Cyberpunk 2077, `<сборка>` папка сборки внутри `ExMods`, `<экземпляр>` папка экземпляра MO2.

## Vortex

### Манифест деплоя

Файл `<игра>\vortex.deployment.json`. Его создаёт Vortex при Deploy. Без него Vortex-источник не работает (UI показывает "нет vortex.deployment.json: сделай Deploy в Vortex").

Читаются ровно эти ключи:

| Ключ | Тип | Как используем |
|---|---|---|
| `stagingPath` | строка | папка staging, где лежат моды |
| `files` | массив | по записи на каждый задеплоенный файл |
| `files[].relPath` | строка, `/` или `\` | путь файла относительно папки игры. Нормализуется в `\`, нижний регистр |
| `files[].source` | строка | имя папки мода в staging, из которой файл положен в игру |
| `files[].target` | строка | если задана и не пуста, ядро останавливается с ошибкой: такую раскладку оно не знает |

Остальные ключи игнорируются. Из пары (`relPath`, `source`) получается карта "кто победил": какой мод Vortex реально положил файл в игру. Множество `source` определяет, какие моды в staging включены (`dep`). Папки staging, которых нет в манифесте, переносятся выключенными. Записи манифеста, у которых в staging нет мода, дают предупреждение "мод из манифеста не найден в папке модов".

Что при изменении:

| Изменение | Симптом |
|---|---|
| ключи переименованы | ошибка "в vortex.deployment.json нет stagingPath/files" или "запись манифеста без relPath/source" |
| у файлов появился `target` | ошибка `target="..." в манифесте, такую раскладку не знаю` |
| манифест в другом месте | "не открыть <игра>\vortex.deployment.json" |
| `source` перестал совпадать с именем папки в staging | предупреждение "записей манифеста не сходятся с папкой модов", победители определяются неверно |

Проверялось на Vortex 2.10.x (бета) с деплоем жёсткими ссылками. Другие способы деплоя (симлинки, копирование) не проверялись.

### Staging

`<stagingPath>\<source>\<relPath>`. Папки, имена которых начинаются с `__`, пропускаются. Ссылки (reparse point) внутри модов пропускаются с предупреждением.

Имя папки мода (разбор `nm`) в трёх вариантах:

| Вариант | Пример | Что берём |
|---|---|---|
| Vortex | `Имя мода-6423-1-4-2--1740164701` | имя, Nexus id, версия (дефисы в точки), дата из unixtime |
| свободное | `Имя v1.2 4591 2.92 2026-10-25T20-46Z хвост` | имя, версия, id, дата |
| ручное | `Имя 5.3.1` | имя и версия, id нет |

Версия из имени папки может быть неверной: Vortex обновляет файлы мода "на месте", имя остаётся старым. Поэтому, если в моде ровно один `red4ext\plugins\<плагин>\<имя>.dll` и версия в его ресурсе новее, берётся она (`dllver`). Если регулярки перестанут совпадать, id и версия окажутся пустыми, а дубли будут искаться только по имени папки.

### База состояния Vortex

Живая база Vortex лежит в LevelDB, её не читаем. Берём самый свежий по времени записи файл из `%APPDATA%\Vortex\temp\state_backups_full\*.json` (`hourly.json`, `startup.json`), поэтому данные могут немного отставать. Нет файла или он битый: предупреждение, версия и Nexus id берутся из имени папки через `nm`.

Функция `vmeta`, ветка `persistent.mods.cyberpunk2077.<папка мода>`, поле `attributes`:

| ключ | куда в `_mod_meta.json` |
|---|---|
| `modId`, при `source` = `nexus` и `downloadGame` = `cyberpunk2077` | `nexusModId`, иначе `homepage` идёт в `sourceUrl` |
| `version`, без точек в конце | `version`, `dllver` может поднять её для плагинов RED4ext |
| `fileId`, `fileName` | `nexusFileId`, `nexusFileName` |
| `uploadedTimestamp` | `nexusFileUploadedAt` |
| `author`, если пусто `uploader` | `author` |
| `shortDescription` | `description` |
| `customFileName` | `displayName` |
| `pictureUrl`, `modName` | `pictureUrl`, `nexusName` |
| `installerChoices` | `fomod`, см. раздел про FOMOD в `_mod_meta.json` |

Архив установки: `persistent.downloads.files.<archiveId>.localPath` внутри `<settings.downloads.path>\cyberpunk2077`, `{USERDATA}` заменяется на `%APPDATA%\Vortex`.

### Следы Vortex в игре (для очистки)

* Файлы в папке игры, которые являются жёсткими ссылками на файлы staging.
* Метки `__folder_managed_by_vortex` внутри каталогов `archive`, `bin`, `engine`, `mods`, `r6`, `red4ext`.
* Файлы `<имя>.vortex_backup` рядом с файлами, подменяющими оригинал игры.

Очистка опирается на то, что файл в игре и файл в staging один и тот же (том и индекс файла). Если Vortex перестанет использовать жёсткие ссылки, все файлы окажутся "изменёнными после deploy", и ничего не будет перенесено в карантин (безопасная сторона отказа).

## Mod Organizer 2

Поддержка написана по исходникам MO2 (`modorganizer`, `modorganizer-uibase`, `usvfs`, плагин игры `modorganizer-basic_games`) и проверена синтетическими каталогами из `tests/mo2.mjs` и `analyzer/test.mjs`. С настоящим MO2 не запускалась. Все утверждения ниже взяты из исходников, места, где они не подтверждены, помечены "не проверено".

### Экземпляр и ModOrganizer.ini

Экземпляр это папка с `ModOrganizer.ini`. Портативный экземпляр: ini рядом с `ModOrganizer.exe`. Глобальный: `<корень>\<имя>\ModOrganizer.ini`, корень по исходникам это `QStandardPaths::AppLocalDataLocation`. UI ищет глобальные экземпляры в `%LOCALAPPDATA%\ModOrganizer\*`. Точное имя корня зависит от имени приложения в Qt, в исходниках оно не задано явно: не проверено. Файл `portable.txt` маркером портативности не служит, это замок, запрещающий переключать экземпляры.

Файл в формате `QSettings::IniFormat`. Особенности, которые разбирают `qini` / `qv` в ядре и `ini` / `val` в `analyzer/mo2.mjs`:

* секции `[General]`, `[Settings]`, `[Plugins]`; ключи без секции относятся к `General`;
* значения-байты вида `@ByteArray(...)` (так MO2 хранит `gamePath` и `selected_profile`), внутри UTF-8 байты в трёх представлениях: Qt 5 (`\xd0\x98`), Qt 6 (двойное кодирование), чистые символы;
* `\\` в путях, `\n`, `\t`, `\xNNNN`;
* имена с `%XX` (ядро и анализатор) и `%UXXXX` (только анализатор): Qt кодирует пробелы в именах групп, например `Cyberpunk%202077%20Support%20Plugin`;
* кавычки вокруг значения.

Используемые ключи:

| Секция/ключ | Что значит | Если нет |
|---|---|---|
| `General/gameName` | должно быть `Cyberpunk 2077` (без учёта регистра) | ошибка "этот экземпляр MO2 не для Cyberpunk 2077" |
| `General/gamePath` | путь к игре. Нужен, если папка игры не указана в командной строке | ошибка "не найдена игра, проверь путь в MO2 или укажи папку игры" |
| `General/selected_profile` | профиль по умолчанию | `Default` |
| `Settings/base_directory` | база для относительных путей | папка с ini |
| `Settings/mod_directory` | папка `mods` | `%BASE_DIR%/mods` |
| `Settings/profiles_directory` | папка профилей | `%BASE_DIR%/profiles` |
| `Settings/overwrite_directory` | папка overwrite | `%BASE_DIR%/overwrite` |
| `Plugins/...enforce_archive_load_order` | включён ли у плагина игры собственный порядок архивов | считается выключенным |

`%BASE_DIR%` подставляется текстом; абсолютные пути (диск или `\`) берутся как есть; относительный путь без `%BASE_DIR%` считается от base. Что MO2 делает с таким путём сам, не проверено. Точное имя группы настроек плагина (`Plugins/<имя плагина>/enforce_archive_load_order`) тоже не проверено, поэтому ядро смотрит на любой ключ в секции `plugins`, оканчивающийся на `enforce_archive_load_order`.

Что при изменении: ключи путей переименованы, значит пути упадут на умолчания, перенос покажет "нет папки модов" или найдёт пустой каталог. Смена кодирования значений: пути с кириллицей станут нечитаемыми, ищи ошибку "не найдена игра...".

### profiles/<профиль>/modlist.txt

* UTF-8, строки через `\n` или `\r\n`, пустые строки и строки на `#` пропускаются, BOM в начале снимается.
* Первый символ строки: `+` включён, `-` выключен, `*` внешний (в исходниках для игр с DLC-плагинами; для Cyberpunk не встречается), без префикса включён. Дальше имя папки мода в `mods\`, без экранирования.
* Порядок обратный: первая строка самая приоритетная и побеждает при конфликте. Ядро разворачивает: `pri = n - i`. В графическом списке MO2 нижняя строка имеет наибольший приоритет, в файле она первая.
* Дубликаты имён (без учёта регистра): остаётся первый. Строка `overwrite` отбрасывается (Overwrite в modlist.txt не пишется).
* Строка без папки в `mods\` ядро пропускает с предупреждением "мод из modlist.txt не найден в папке модов".
* Папка в `mods\`, которой нет в modlist.txt, MO2 считает выключенной; ядро переносит её выключенной.

Что при изменении: поменяется порядок (инверсия), все победители в конфликтах будут обратными. Тест `tests/mo2.mjs` проверяет порядок явно (`priority lost: High must deploy after Low`), а событие `verify` в каждом прогоне сверяет победителей.

### Папки в mods\

| Что | Что делаем | Почему |
|---|---|---|
| имя на `_separator` | не мод, превращается в разделитель категории | в MO2 это разделитель в списке, файлов нет |
| имя оканчивается на `backup` с цифрами (`.*backup[0-9]*`) | пропуск | резервные копии MO2 не деплоятся |
| папка с атрибутом "скрытая" | пропуск | MO2 такие не сканирует |
| `disable CrashReporter (MO CET fix)` | пропуск | служебная заглушка плагина игры |
| имя начинается с `_` | переносится с префиксом `m` (`m_Имя`) | лаунчер не видит папки на `_` |
| после фильтрации файлов пусто | пропуск | нечего деплоить |

### meta.ini мода

Читается через тот же `qini`. Используемые ключи (все в секции `General`):

| Ключ | Что делаем |
|---|---|
| `modid` | Nexus id, если больше 0 и `gameName` пуст или `cyberpunk2077`, а `repository` пуст или `Nexus` |
| `version` | чистится `mver` (убирается схема `f`/`n`/`d`, `v`, хвостовые `.0`) |
| `installationFile` | имя файла Nexus. Если по нему видно тот же id и дату (шаблон `имя-id-версия-unixtime`), версия и дата берутся из имени. Имя файла (без пути) идёт в `nexusFileName` |
| `[installedFiles]` `size`, `N\modid`, `N\fileid` | `nexusFileId` для того же `modid` |
| `comments` | в описание |
| `author` | в автора |
| `url` | в `sourceUrl`, только если Nexus id нет |

Не используем: `category`, `notes`, `newestVersion`, `endorsed`, `tracked`, `nexusFileStatus`, `color` и прочее. Файлов `downloads\*.meta` ядро не читает.

Если `meta.ini` нет совсем, мод переносится без Nexus-данных. Версия MO2 (`d2024.1.2`, `f1.05`) превращается в обычную строку.

### Файлы мода: что отбрасываем

`mfilt` для обычных модов:

| Отбрасывается | Почему |
|---|---|
| `*.mohidden` | так MO2 прячет файл; в игре его нет |
| `meta.ini`, `readme.txt` в корне мода | служебное MO2 |
| `fomod\*` в корне | данные установщика |
| `.git\` где угодно | в MO2 пропускается по умолчанию |
| `archive\pc\mod\modlist.txt` | порядок архивов лаунчер пишет сам |

Развёртка `root\`: файлы под `root\` переезжают в корень мода (старое соглашение RootBuilder). Физически файл остаётся по старому пути, `F::up` хранит признак.

Overwrite (папка `overwrite_directory`, MO2 добавляет её как мод с наивысшим приоритетом, в modlist.txt её нет) читается как мод `MO2 Overwrite` с теми же фильтрами плюс: логи и дампы (`*.log`, `*.dmp`), `r6\cache\`, `r6\logs\`, `red4ext\logs\`, `logs\`. Они создаются игрой и инструментами, переносить их смысла нет. Например, настройки CET из Overwrite переносятся.

Корень мода MO2 соответствует корню игры (плагин игры задаёт `GameDataPath = %GAME_PATH%`), поэтому `archive\pc\mod\x.archive` в моде означает `<игра>\archive\pc\mod\x.archive`. Если у мода под корнем лежит что-то, кроме `archive`, `bin`, `engine`, `mods`, `r6`, `red4ext`, `tools` (документы не считаются), ядро предупреждает "мод лежит не от корня игры".

### Порядок архивов

В MO2 порядок архивов по умолчанию не пишется. Если у плагина игры включён `enforce_archive_load_order`, MO2 пишет `archive\pc\mod\modlist.txt` по приоритетам. У лаунчера порядок архивов всегда по имени (см. ниже). Ядро в этом случае предупреждает, что у каких-то пар модов победитель может смениться, и не пытается этого исправить. Смысл порядка в этом файле на стороне игры по исходникам MO2 не подтверждается: не проверено.

### REDmod

Моды вида `mods\<имя>\info.json` переносятся как файлы. Файл порядка REDmod (`MO_REDmod_load_order.txt`) не используется. Порядок REDmod лаунчер определяет по порядку активаций.

### Профильные данные

Не переносятся, только предупреждения: `profiles\<имя>\saves` при `LocalSaves=true` в `settings.ini` профиля; `UserSettings.json` в папке профиля.

## Сборка ExLauncher

Кодировка файлов UTF-8, лаунчер пишет их с отступами, мы пишем компактно (читается лаунчером без проблем; он перезапишет файл при первом же действии). Ключи в json camelCase. Чтение в ядре регистр ключей не различает (`J::at`).

Версия лаунчера, по которой сверялись форматы, в репозитории не зафиксирована. Если форматы разойдутся, см. `MAINTAINING.md`, "После обновления ExLauncher".

### Дерево

```
ExMods\                         корень сборок (рядом с игрой в steamapps\common\ExLauncher Mods\Cyberpunk 2077\ExMods)
  <сборка>\
    _build_info.json
    _build_meta.json
    _activation_state.json
    _profiles.json
    <категория>\
      _category.json
      <мод>\
        _mod_meta.json
        _mod_snapshot.json
        ...файлы мода относительно корня игры
```

Любая папка на `_` лаунчеру не видна как сборка, категория или мод. Категория это любая подпапка сборки без `_`, мод это любая подпапка категории без `_`. Категория существует с момента появления папки, `_category.json` необязателен. Сборку лаунчер узнаёт по `_build_info.json`; ядро считает папку сборкой, если есть `_build_info.json`, `_profiles.json` или `_activation_state.json`, иначе ошибка "папка есть, но это не сборка exlauncher".

Имя папки новой сборки: `[A-Za-z0-9_-]+` (так проверяет и лаунчер при создании в интерфейсе). Названия категорий, которые создаёт ядро: `Vortex`, `Vortex2`, ... или `MO2`, `MO2-2`, ...

Служебные имена, которые не деплоятся и не учитываются как файлы мода (`svc` в ядре): `_mod_meta.json`, `_mod_snapshot.json`, `_structure_repair.json`, `_origin.json`, `_category.json`, `_build_meta.json`, `_build_info.json`, `_archive_info.json`, `_builds_order.json`, `_installed_manifest.json`, `_activation_state.json`, `_profiles.json`, `_launch_*.json`, `_runtime_additions.json`, `_modscache_migrated.json`, `_release_plan.json`, `_release_history.json`, `_mod_history.json` (и `.bak`, `.tmp`, `.broken`), папки `_saved_configs`, `_addon_backup`, `_diagnostics`, `_settings_backup`, `_releases`, `_preview`, `_stale`, `_replaced`, `_native`, `_unsorted`, `_optimize_backup`, `_variants`. Если во входящем моде встретится файл или папка с таким именем, ядро предупредит "служебное имя exlauncher, не задеплоится".

### _activation_state.json

```json
{"buildName": "<сборка>",
 "activations": [{"categoryName": "<категория>", "folderName": "<мод>", "enabled": true, "order": 0}],
 "savedAt": "2026-01-01T00:00:00Z"}
```

Порядок элементов массива это порядок деплоя, последний побеждает. `order` ядро заполняет индексом (на деплой не влияет, но интерфейс его сортирует). `enabled` читается как bool или как строка `"1"`/`"true"`. Для существующих записей ядро сохраняет все остальные поля, меняет только `enabled` и `order`. Записи на несуществующие папки лаунчер не терпит: при сохранении активаций он отвергает набор, где пропавших папок больше чем max(3, 10 процентов).

### _profiles.json

```json
{"activeProfile": "<имя>", "profiles": {"<имя>": {"name": "<имя>", "activations": [ ... как выше ... ]}}}
```

Слияние в существующую сборку: добавляется профиль `<активный> + Vortex` (или `+ MO2`, при повторе с номером), в него копируется итоговый набор активаций, он становится активным. В остальные профили добавляются входящие моды с `enabled:false` и `order` после последнего. Для новой сборки профиль по умолчанию `default`. Ядро отказывается писать, если активный профиль расходится с `_activation_state.json` (сравнение после сортировки по `order`; сообщение "активный профиль не совпадает с _activation_state.json, переключи профиль в лаунчере туда-обратно").

### _build_meta.json

`{"categoryOrder": ["<категория>", ...]}`. Ядро добавляет новую категорию в конец. Список порядка категорий и `modOrder` в `_category.json` должны быть без повторов (повтор по исходному коду лаунчера приводит к исключению при построении списка).

### _build_info.json

Пишется только для новой сборки: `{"buildId": "<guid>", "displayName": "<имя>", "description": "из Vortex <время>"}`. UI читает `displayName` и `version`.

### <категория>\_category.json

`{"modOrder": [...папки модов и "__sep__<guid>"...], "separators": [{"id": "__sep__<guid>", "title": "<название>", "lineColor": "", "titleColor": ""}]}`. Ядро пишет только эти два ключа (и `separators` только для MO2). Лаунчер может хранить также `description`, `color`, `isSystem`, `excludeFromRelease`. Порядок `modOrder` возрастающий по приоритету, разделитель MO2 ставится перед первым модом, чей приоритет не меньше приоритета разделителя. Работу лаунчера именно с такими разделителями в живую не проверяли: не проверено.

### <мод>\_mod_meta.json

Ядро пишет такие ключи (в этом порядке):

| Ключ | Откуда |
|---|---|
| `originalName` | имя папки источника |
| `displayName` | разобранное имя мода (для замены мода сборки: его прежнее имя) |
| `origin` | `"user"` |
| `installedAt` | время переноса, ISO UTC |
| `version` | версия, если есть |
| `description` | причина выключения ("выключен при переносе: ...") либо описание/комментарий источника |
| `author` | автор (MO2) |
| `nexusModId` | **строка** с числом |
| `nexusGameDomain` | `"cyberpunk2077"` |
| `sourceUrl` | `https://www.nexusmods.com/cyberpunk2077/mods/<id>`; без Nexus id берётся `url` из `meta.ini` |
| `nexusFileUploadedAt` | дата `ГГГГ-ММ-ДД` |
| `nexusFileId` | **строка**, если известен |
| `nexusFileName` | имя файла Nexus, если известно |
| `addons` | перенесённые дополнения мода сборки (объекты как были) |

Что лаунчер делает с этим (по его коду): проверка обновлений требует непустых `nexusModId` и `nexusGameDomain` и сравнивает только `version` (пустая версия означает вечное "есть обновление"). Поиск дубликатов при установке сравнивает `nexusModId`, а если `nexusFileId` и `nexusFileName` оба пусты, считает совпавшим любой файл этой страницы Nexus, поэтому их стоит заполнять, когда они известны. Остальные ключи лаунчера (`ignoreUpdatesUntil`, `manualEdits`, `fomod` и т. д.) ядро не пишет, читатель в лаунчере терпим к их отсутствию. Мод без `_mod_meta.json` лаунчер показывает по имени папки.

Читает ядро у модов сборки: `originalName`, `nexusModId`, `displayName`, `version`, `description`, `nexusFileUploadedAt` (иначе `installedAt`), `addons[]` с полями `type`, `displayName`, `replacedFiles`, `addedFiles`.

### FOMOD в `_mod_meta.json`

Поле `fomod`: `{moduleName, installedAt, choices: [{stepName, groupName, pluginId, pluginName}]}`, `pluginId` у нас это `idx` из Vortex. Лаунчер повторяет выбор при обновлении только по `pluginName`, причём по всем группам сразу: одинаковое имя в другой группе ломает выбор, и группа сбрасывается на вариант по умолчанию. Без поля `fomod` обновление ставит архив как есть.

Поэтому `fsafe` читает `fomod/ModuleConfig.xml` из исходного архива (`fcfg`, через системный `tar.exe`) и проверяет, что в каждой группе отметятся ровно те опции, что были выбраны. Не прошло или архива нет: выбор всё равно пишется, а в `ignoreUpdatesUntil` ставится 2036 год, чтобы "Обновить всё" не трогало мод.

MO2 выборы установщика нигде не хранит (в исходниках `installer_fomod` их записи нет), поэтому переносить нечего. Мод с Nexus id считается FOMOD-модом, если в его папке есть `fomod\` или в архиве из `downloads` есть `fomod/ModuleConfig.xml`. Такие моды замораживаются.

### <мод>\_mod_snapshot.json

`{"snapshotAt": "ГГГГ-ММ-ДДTчч:мм:сс", "installMethod": "folder", "files": [{"path": "относительный/путь", "hash": "<sha256 строчными>", "size": N}]}`. Пути с `/`, регистр как на диске. Пишется после того, как раскладка файлов окончательная. Нужен лаунчеру для сравнения "что поменялось в папке мода". Лаунчер считает файл изменённым, если размер другой, либо mtime позже `snapshotAt` плюс 2 секунды и хэш другой. Ядро пишет `snapshotAt` во времени UTC, а лаунчер, по его коду, сравнивает с локальным; на практике это безвредно, потому что при совпадении хэша файл изменённым не считается, но на машине в часовом поясе, далёком от UTC, не проверялось.

### Деплой лаунчера (что важно знать при записи)

* Деплой по порядку массива активаций, последний побеждает. Файл, который уже лежит в игре как настоящий (не ссылка) на месте `.archive`, пропускается, раньше установленный остаётся.
* Символической ссылкой ставятся только `*.archive` (кроме `red4ext\plugins\*\resources`). Всё остальное копируется при запуске игры и удаляется после; изменённые пользовательские файлы (расширения json, ini, cfg, xml, yaml, yml, toml, lua, sqlite*, db, dat) сохраняются в `<мод>\_saved_configs`.
* `archive\pc\mod\modlist.txt` лаунчер пишет сам: имена всех `*.archive` включённых модов, по алфавиту (Ordinal), без повторов. Приоритета модов в нём нет. Два мода с архивом одного имени сливаются в одну запись, файл остаётся у позднего.
* REDmod: при запуске `redMod.exe deploy` для модов, у которых есть `mods\<имя>\info.json`, в порядке активаций.
* Лаунчер при любом действии в интерфейсе может перезаписать `_activation_state.json` и `_category.json`. Поэтому ядро отказывается работать при запущенном лаунчере.
* Конфликтов лаунчер сам не анализирует, кроме байтового сравнения файлов по запросу (до 64 МБ).

## Индекс RDAR (`.archive`)

Читаем только индекс, содержимое ресурсов не распаковываем (кроме заголовков, см. анализатор).

Заголовок 40 байт: `u32` сигнатура `RDAR` (0x52414452) со смещения 0, `i64` смещение индекса со смещения 8, `u32` размер индекса со смещения 16.

Индекс (размер `n`, должен совпасть с суммой частей, ядро это проверяет и отбрасывает архив, если не совпало):

| Смещение | Содержимое |
|---|---|
| 16 | `u32` число файлов `nf` |
| 20 | `u32` число сегментов `ns` |
| 24 | `u32` число зависимостей `nd` |
| 28 | `nf` записей по 56 байт |
| 28 + 56·nf | `ns` сегментов по 16 байт |
| далее | `nd` значений `u64` (хэши путей, на которые ссылается архив) |

`28 + nf·56 + ns·16 + nd·8` должно равняться размеру индекса.

Запись файла (56 байт): `u64` хэш пути со смещения 0 (FNV-1a 64 бита от пути в нижнем регистре с `\` вместо `/`; у слов вне ASCII хэшируются байты UTF-8); `i64` время (FILETIME, 100 нс от 1601 года) со смещения 8; `u32` номер первого сегмента (смещение 20); `u32` номер последнего плюс один (смещение 24); 8 байт контрольной суммы содержимого со смещения 36.

Сегмент (16 байт): `u64` смещение в файле, `u32` размер сжатого, `u32` размер распакованного. Первый сегмент файла это основные данные, остальные это дополнительные буферы (используются для мешей и пакетов внешностей).

Что использует ядро: только `u64` хэши (`rdar`). Анализатор: всё перечисленное (`idx`), плюс индекс игры для снимков.

Что при изменении: сигнатура или размеры не сошлись, `rdar` / `idx` возвращают пусто. В ядре это молча означает "конфликтов ресурсов архивов нет"; в анализаторе архив не индексируется (`arcInfo` ловит ошибку), и пропадают `archive-overlap`. Если после патча анализатор внезапно показывает ноль перекрытий архивов, проверь это первым.

### Сжатие и CR2W

Данные сегментов сжаты Oodle. Распаковывает C#-помощник через `oo2ext_7_win64.dll` из `<игра>\bin\x64`, функция `OodleLZ_Decompress` (14 параметров, соглашение cdecl; сигнатура зашита в строке `OO` в `analyzer/rdar.mjs`). Если сегмент начинается с `KARK`, первые 8 байт пропускаются, размер распакованного в них же. Если размеры сжатого и распакованного равны, данные считаются несжатыми.

CR2W (формат ресурса после распаковки): сигнатура `CR2W` (0x57325243). Читаемые поля заголовка (все `u32` LE): смещение 40 таблица строк, 52 таблица имён (записи по 8 байт), 64 таблица импортов (записи по 8 байт, число на 68), 88 таблица экспортов (записи по 24 байта, число на 92), 100 и 104 для секторов (`sectorNodes`: по смещению из поля 100 читается `u32` на +16, при ненулевом поле 104; частное от деления на 144 это число узлов сектора, если делится нацело, иначе результат пуст; что это за таблица, в коде не названо). Импорт: `u32` смещение строки пути, на байтах 6-7 флаги; импорты с флагом 8 не считаются обязательными. Класс ресурса это имя первого экспорта. Для внешностей читаются свойства (`appLoose`), для пакетов `compiledData` версии 4 с семью секциями (`pkgRefs`).

Что при изменении: `cr2w` вернёт `null` для ресурсов с неизвестной сигнатурой; сломается вывод класса и ссылок, анализатор станет выдавать меньше `dangling-ref` (молчание) или лишние `dangling-ref` (шум). Проверка: `analyzer/bench.mjs` на известной сборке, либо руками сравнить число узлов известного сектора.

## Снимок игры (кэш анализатора)

* `vanilla.bin`: заголовок 48 байт (40 символов ключа sha1 по списку ванильных архивов с размерами и mtime, `u32` число ресурсов, `u32` число зависимостей), затем массивы хэшей, контрольных сумм, зависимостей, размеров.
* `fp-<версия игры>-<ггггммдд>.bin.gz`: gzip; записи по 20 байт: `u64` хэш, `u32` размер, `u64` контрольная сумма. Версия из ресурса `Cyberpunk2077.exe` (ProductVersion, иначе FileVersion), дата это mtime exe.
* `arc\<sha1 пути>.json`: индекс архива мода, ключ `v3:<размер>:<mtime>`.
* `files.json`: разборы `.xl`, твиков, Lua, `.reds`, PE (`v` = `PV`).
* `vrefs.json`: ссылки ванильных ресурсов и число узлов секторов (ключ `v4:<версия>@<дата патча>`).
* `scc.json`, `scc\`: результат компиляции скриптов и рабочая копия.
* `oo-<hash>.exe`: скомпилированный C#-помощник (хэш от его исходника).

Менять формат кэша: поднимай префикс ключа (`v3`, `v4`) или `PV`, старые файлы тогда игнорируются.

## Словарь путей

Хэш пути в RDAR односторонний. Чтобы показывать имена, нужен словарь: `analyzer/paths.data.mjs` содержит `export default '<base64>'`; это brotli от текста, по пути в строке, в нижнем регистре, с `\`. Источник: список путей из WolvenKit, отфильтрованный по хэшам, реально присутствующим в ванильных архивах (`analyzer/mkdict.mjs`). Файл около 2,9 МБ, лицензия GPL-3.0 (данные WolvenKit).

Без записи в словаре ресурс показывается как `0x<хэш>`, не получает категорию по пути и не попадает в ряд проверок, которым нужен путь (`stale-replacer` по группам, `dangling-ref` по расширению). Часть имён докладывается из ссылок внутри архивов модов.

## ArchiveXL: `.xl`

YAML-файлы (иногда JSON), которые читает ArchiveXL. Разбирается самодельным разборщиком (`yaml()` в `analyzer/scan.mjs`), знающим подмножество: блоки, списки, потоковые `[]` и `{}`, теги `!имя`, строки в кавычках, многострочные скаляры. Ключи, которые использует анализатор (`xlPaths`):

| Ключ | Что значит для анализатора |
|---|---|
| `streaming.sectors[]`: `path`, `expectedNodes`, `nodeDeletions[]` (`index`, `type`), `nodeMutations[]` | правка сектора мира. Проверяется существование сектора и совпадение `expectedNodes` с числом узлов в игре |
| `streaming.blocks[]` | блоки стриминга. Проверяется существование |
| `resource.patch` (цель: список источников) | подмена ресурсов |
| `resource.scope`, `resource.fix` | ссылки на ресурсы |
| `resource.link`, `resource.copy` | ресурсы, которые мод "предоставляет" (считаются существующими) |
| `localization`, `factories`, `customizations`, `journal`, `quest` | пути из строк (с `\` и расширением) считаются ссылками |

Что при изменении: ArchiveXL добавляет или переименовывает секции. Анализатор их просто не увидит (меньше ссылок, молчание). Файл с новым синтаксисом YAML даст `tweak-invalid` "файл ArchiveXL не читается" с номером строки.

## Твики (TweakXL) и скрипты

* Твики: `.yaml` / `.yml` в `r6\tweaks\` или `mods\<имя>\tweaks\`. Ключи с точкой это записи TweakDB; `$type` / `$base` делают запись объявлением, вложенные поля становятся плоскими ключами `Запись.поле`. Теги слияния `!append`, `!append-once`, `!prepend`, `!prepend-once`, `!remove`, `!merge` и подстановки `$(` исключают ключ из сравнения. Идентификатор TweakDB в отчётах: crc32 имени плюс длина в старших битах.
* Lua CET (`bin\x64\plugins\cyber_engine_tweaks\mods\**\*.lua`): `Override("Класс","метод",...)`, `Observe`, `ObserveAfter`, `ObserveBefore`, `TweakDB:SetFlat("ключ", значение)`.
* redscript (`.reds`): `module X.Y`, `import X.Y(.*|.{...})`, аннотации `@replaceMethod`, `@wrapMethod`, `@replaceGlobal`, `@wrapGlobal` (комментарии `//` и `/* */` вырезаются).
* Компиляция скриптов (ядро: `--check`, анализатор: `reds-compile`). Рабочее дерево во временной папке:
  * `r6\cache\final.redscripts` и `final.redscripts.bk` копируются из игры (кэш скриптов ванили для текущей версии);
  * `r6\scripts\<путь>` берётся из включённых модов (`r6\scripts\*.reds`), побеждает последний;
  * `.reds` из `red4ext\plugins\<...>` кладутся в `r6\scripts\__plugins\<...>` (в ядре и анализаторе), `mods\<m>\scripts\...` в `__redmod` (только анализатор);
  * `scc_lib.dll` берётся из `engine\tools\scc_lib.dll` одного из включённых модов (redscript в сборке ExLauncher лежит как мод);
  * выходной файл `out\final.redscripts` не используется, нужен только код возврата и лог;
  * из лога берутся строки вида `[ERROR...] [КОД] At <файл>:<строка>:<колонка>:`, текст ошибки это третья строка после неё.
* Вызовы библиотеки: `scc_settings_new(r6)`, `scc_settings_set_output_cache_file(s, out)`, `scc_settings_disable_error_popup(s)`, `scc_compile(s)`, `scc_get_success(r)`. Окно с ошибкой компиляции рисует сама `scc_lib`, поэтому вызов `disable_error_popup` обязателен.

Что при изменении: переименована функция в `scc_lib`: `--scc` вернёт 3, ядро скажет "scc_lib не отработал, код 3", а `--check` не запустится. Кэш скриптов новой версии игры несовместим со старой `scc_lib`: компиляция падает у самой сборки ("сборка и без вортекса не компилируется"), пока не обновлён redscript. Формат строки ошибки поменялся: ошибки не распознаются, вместо них одна строка "компиляция не прошла, лог: ..." с путём к логу.
