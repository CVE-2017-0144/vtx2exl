# Архитектура

## Состав

| Часть | Где | Язык | Что делает |
|---|---|---|---|
| Ядро | `src/vtx2exl.cpp`, `src/crc32c.asm` | C++20 + MASM x64 | Читает Vortex или MO2 и сборку ExLauncher, находит конфликты, пишет сборку, откатывает, чистит папку игры |
| Протокол | `src/events.txt` | текст | Описание NDJSON, который ядро пишет при `--json` |
| UI | `ui/` | JS (JSX), Bun + Ink 5 | Мастер переноса, откат, очистка, карта конфликтов. Собирается в один exe, ядро внутри |
| Анализатор | `analyzer/` | JS (ESM), без npm-зависимостей | Ищет конфликты и поломки внутри уже собранной сборки или профиля MO2 |
| Вьюхи | `proto/whales`, `proto/graph` | JS, Ink | Киты на главном экране, граф проблем на карте |
| Тесты | `tests/mo2.mjs`, `ui/*.test.*`, `analyzer/test.mjs`, `proto/*/test.mjs`, `--selftest` | | См. `MAINTAINING.md` |

Ядро ничего не знает про UI и анализатор. UI может вообще не запускать анализатор. Анализатор из ядра использует только один режим: `--scc` (компиляция redscript в отдельном процессе).

## Как части общаются

```
VTX2EXL-UI.exe (Bun, один процесс)
  ├─ spawn: vtx2exl.exe <args> --json      NDJSON в stdout, человеческий текст в stderr
  │     (ядро вытащено из exe в %LOCALAPPDATA%\vtx2exl\bin\<sha256[0:12]>\vtx2exl.exe)
  ├─ spawn: VTX2EXL-UI.exe --an '<json>'   тот же exe в режиме анализатора, прогресс NDJSON в stdout,
  │     │                                  результат файлом ui-graph.json в кэше
  │     └─ analyzer/index.mjs → check.mjs → rdar.mjs / scan.mjs
  │            └─ spawn: vtx2exl.exe --scc <scc_lib.dll> <r6> <out>   (компиляция скриптов)
  │            └─ spawn: oo-<hash>.exe (C#-помощник, собирается csc.exe)  (распаковка Oodle)
  └─ файлы: _exfix\cmd\*.json в папке ExMods (если лаунчер открыт и пропатчен), либо прямая правка json сборки
```

Ядро, режимы `wmain`:

| Аргументы | Режим |
|---|---|
| `<игра> <сборка> [ключи]` | перенос из Vortex |
| `--mo2 <экземпляр> [--profile имя] [<игра>] <сборка> [ключи]` | перенос из MO2. Папка игры необязательна, берётся из `gamePath` |
| `--undo <сборка> [--apply]` | откат последнего переноса |
| `--purge <игра> [--apply]` | убрать файлы Vortex из игры в карантин. Для MO2 отказ |
| `--selftest` | встроенные проверки |
| `--scc <lib> <r6> <out>` | внутренний режим (`argc == 5`). Компилирует скрипты и возвращает код |

Ключи переноса: `--apply` (без него только план), `--keep` / `--take` / `--vortex` (политика конфликтов), `--check` (компиляция скриптов, при `--apply` включена всегда), `--extra <папка>` (повторяется, дополнительные папки с модами, каждая подпапка это мод), `--name` (отображаемое имя новой сборки), `--decisions <файл.json>` (ручные решения, только вместе с политикой), `--json`.

Политика в коде это `pol`: 1 keep, 2 take, 4 vortex, 0 не задана. Значение 3 возникает только внутри `run()` как ответ "решить по каждому" на интерактивный вопрос. Для MO2 слово "vortex" в ключе и в `policy` остаётся, смысл: побеждает входящий источник (при `--vortex` новее).

Код возврата: 0 успех, 1 ошибка (`Err`), 2 неверные аргументы, у `--selftest` число проваленных проверок. `done` всегда последнее событие.

### Вывод ядра

При `--json` в `wmain` стандартный вывод дублируется (`_dup(1)`) в дескриптор `jo`, после чего fd 1 перенаправляется на fd 2. Поэтому всё, что идёт через `wprintf`, попадает в stderr, а события пишет только функция `ev()` в `jo`. Событие это объект, собранный классом `O` (`O("warn").s("msg", m).go()`), одна строка на событие, сразу сброшена. Спецификация событий в `src/events.txt`. UI разбирает строки в `S.run` (`ui/sys.js`) и сворачивает события в состояние задачи в `feed()` (`ui/job.jsx`). Строка, которая не разобралась как JSON с полем `t`, показывается в журнале как `raw`.

Протокол версии 1 (`start.v`). UI версию не проверяет.

| Кэш анализатора | `<база>\cache` (при запуске из UI), у отдельного `node analyzer/index.mjs` по умолчанию тот же путь `%LOCALAPPDATA%\vtx2exl\cache`, у `mkdict.mjs` другой: `%LOCALAPPDATA%\vtx2exl\analyzer` |

| Рабочая копия проверки скриптов в ядре | `%TEMP%\vtx2exl_chk`, удаляется после |
| Бэкап переноса | `<ExMods>\_vtx2exl.backup\<сборка>-<ггггммдд-ччммсс>` |
| Бэкап правок UI | `<ExMods>\_vtx2exl.backup\ui-fixes\<метка>` |
| Откаченные моды | `<ExMods>\_vtx2exl.undone\<бэкап>-<категория>` |

Кэш можно удалять целиком. Платой будет полный пересчёт: индекс ванильных архивов и разбор архивов модов при первом прогоне долгие. Исключение: снимки `fp-*.bin.gz` в кэше анализатора хранят прошлые версии игры, их потеря означает "нет снимка прошлой версии" (см. `MAINTAINING.md`, "После патча игры").

## Поток одного переноса

Пример для Vortex в существующую сборку. Для MO2 отличается только чтение источника и порядок (см. ниже).

1. UI: пользователь выбирает игру, сборку (или имя новой), режим, дополнительные папки, флаг проверки скриптов. Из этого собираются аргументы (`args` в `Mig`, `ui/app.jsx`).
2. Пробный прогон без `--apply`: `S.run(args)` запускает ядро. Ядро читает источник и сборку, находит конфликты, печатает события `phase`, `progress`, `target`, `conflict`, `mod`, `vconf`, `summary`, `done`. Ничего не записывается. Если политика задана и интерактивных вопросов нет, `conflict` содержит `choice`, `default` и `options`.
3. Экран "Конфликты": пользователь меняет выбор. UI хранит решения как словарь `id -> вариант` (`dec` в `Mig`). Для пересчёта плана решения пишутся в `%TEMP%\vtx2exl-ui-<pid>.json` и передаются как `--decisions`. Меняются решения, значит изменился ключ `key` в `Mig`, план считается устаревшим и пересчитывается (`stale`).
4. Запись: тот же набор аргументов плюс `--apply`. Перед запуском UI проверяет список процессов (`S.procs`, `tasklist`): игра, ExLauncher и менеджер-источник. Ядро со своей стороны отказывается писать при открытом ExLauncher, если идёт слияние в существующую сборку; открытый Vortex или MO2 даёт только предупреждение.
5. Ядро при `--apply`:
   1. проверяет, что ExLauncher не запущен, профиль не расходится с состоянием, нет остатков прошлой попытки;
   2. создаёт рабочую папку рядом со сборкой и кладёт в неё моды (жёсткая ссылка или копия с проверкой crc32c), для каждого мода пишет `_mod_meta.json` и `_mod_snapshot.json`;
   3. строит новые `_activation_state.json`, `_profiles.json`, `_build_meta.json`, `_category.json` в памяти;
   4. перед заменой убеждается, что три json сборки не поменялись с момента чтения;
   5. делает бэкап трёх json и пишет в него `_vtx2exl.json` (категория и профиль, нужные для отката);
   6. переименовывает рабочую папку в `<сборка>\<категория>`;
   7. заменяет три json (временный файл, затем `MoveFileEx` с заменой);
   8. выводит `summary` и `done` (с путями `backup` и `build`).
6. UI показывает итог и кнопки "открыть сборку", "открыть бэкап", "карта конфликтов".
7. Откат (`--undo`) берёт последний бэкап по имени, возвращает три json, уносит категорию в `_vtx2exl.undone`, помечает бэкап суффиксом `.used`. Правки, сделанные в лаунчере после переноса, при откате теряются.

Новая сборка (папка не существует): тот же путь, но без бэкапа и профилей. Ядро пишет `_build_info.json` и три json с нуля, рабочая папка `_vtx2exl_<сборка>` переименовывается в итоговую. Отката для новой сборки нет, её удаляют руками.

### Порядок и победитель

Сборка ExLauncher деплоит моды в порядке массива `activations`, последний побеждает. Поле `order` на деплой не влияет, но ядро его заполняет индексом.

Итоговый порядок строит `order()`: топологическая сортировка модов, в которой ребро `E` идёт от проигравшего файла к победителю. Сначала в массив кладутся выключенные входящие моды, затем остальные в порядке: моды сборки по прежнему индексу, входящие по приоритету (`pri`), при равенстве по имени папки (без учёта регистра); порядок исправляется рёбрами. Ребро добавляется, когда два входящих мода содержат файл с одним путём и разным содержимым: проигравший должен стоять раньше победителя. Победитель определяется источником:

* Vortex: `win[путь]`, строится из `files` манифеста (какой мод в staging лёг в игру).
* MO2: выше приоритет в профиле побеждает; `win` строится из включённых модов по возрастанию `pri`, overwrite последним.

Цепочка `for (int i = 1; i < ne; i++) es.push_back({i - 1, i, -1})` фиксирует прежний порядок модов самой сборки. Если в графе цикл, `order()` режет рёбра проигравших входящих модов (`cut`, файл помечается `drop`, в сборку не попадёт). Режутся только рёбра, у которых проигравший это входящий мод, поэтому файлы сборки не теряются. Событие `vconf` с `cut:true` сообщает о таком файле.

### Что отличается для MO2

* Источник читается из `ModOrganizer.ini` и `profiles/<профиль>/modlist.txt`. Первая строка modlist.txt самая приоритетная, ядро разворачивает порядок: `pri = n - i`, где `i` индекс строки.
* Включён только мод с префиксом `+` (или без префикса). `-` и `*` выключены. Папка из `mods/`, которой нет в modlist.txt, переносится выключенной.
* Разделители (`*_separator`) в моды не попадают, но становятся разделителями категории в `_category.json` (`__sep__<guid>`).
* Overwrite добавляется последним модом `MO2 Overwrite` (приоритет `INT_MAX`), после фильтрации логов и кэша.
* Содержимое `root/` разворачивается в корень мода, файлы `.mohidden`, `meta.ini`, `readme.txt`, `fomod/`, `.git/` отбрасываются (`mfilt`).
* Из `meta.ini` берутся Nexus id, версия, файл установки, комментарий, автор, ссылка (`mmeta`).
* После расчёта порядка идёт сверка `verify`: для каждого файла, который MO2 бы задеплоил, считается, тот ли мод победит в сборке. Поле `diff` не ноль означает баг в порядке.
* Все русские тексты в ядре написаны как для Vortex. В режиме MO2 функция `srn()` подменяет в выводе слова "вортекс" (и формы) и, в форматных строках, "Vortex"/"vortex" на "MO2". Если пишешь новое сообщение с этими словами, помни о подмене.

## Ядро

### Соглашения

* Весь код в одном файле, строки `wstring`, пути в формате `\\?\` (`lp()` приводит к абсолютному виду и добавляет префикс, `disp()` снимает его для показа).
* Ошибка это исключение `Err{сообщение}`. Ловится в `wmain`, пишет `ошибка: ...` в stderr, событие `error`, код 1.
* Файлы читаются целиком (`slurp`), пишутся `spit` (`CREATE_NEW`; с `rep=true` через временный файл с заменой и сбросом на диск).
* Хэш содержимого для сравнения файлов crc32c (`fcrc`) вместе с размером; `crc` выбирается один раз: `crc32c_hw` (инструкция SSE4.2, `src/crc32c.asm`) или таблица `crc32c_sw`, если процессор без SSE4.2. SHA-256 (`sha256`, BCrypt) считается только для `_mod_snapshot.json`.
* `lc()` приведение к нижнему регистру через `CharLowerBuffW`, все ключи файлов (`F::key`) в нижнем регистре.
* `wprintf` переопределён макросом на `pf()`, который прогоняет формат через `srn()` и сбрасывает буфер.
* `lp()` заодно снимает хвостовые кавычки (путь, вставленный из проводника, не ломается).

### Структуры

| Имя | Что это |
|---|---|
| `Err` | исключение с текстом |
| `J` | минимальный JSON-узел: `t` (NUL, BOOL, NUM, STR, ARR, OBJ), `b`, `s` (строка или исходный текст числа), `k` ключи объекта по порядку, `v` значения. Числа хранятся текстом, поэтому json при перезаписи не меняет их вид. `at(ключ)` ищет без учёта регистра, `put` заменяет или добавляет. Порядок ключей сохраняется, неизвестные ключи лаунчера переживают перезапись |
| `JP` | парсер для `J` (`pj(строка)`; пропускает BOM; ошибка "битый json"). Печать: `dump` / `dumps` (компактно, с `\n` в конце) |
| `O` | сборщик одной JSON-строки события: `k`, `s` (строка, проходит `srn`), `a` (ASCII), `n`, `b`, `r` (готовый JSON), `go()` отправляет |
| `F` | файл мода: `rel` путь внутри мода с исходным регистром и `\`, `key` он же в нижнем регистре (идентичность файла в дереве игры), `sz`, `c` (crc32c), `hashed` (посчитаны ли `c` и `sz` через `hc`), `drop` (не копировать, срезан на цикле), `up` (файл лежал под `root\` и был развёрнут; физический путь даёт `fsp()`) |
| `M` | мод. `root` физический каталог, `cat` и `dir` место в сборке, `lid` = `lc(dir)`, `orig` из `originalName`, `name` показываемое имя, `ver`, `desc`, `date` (ГГГГ-ММ-ДД), `why` причина выключения, `nid` Nexus id, `fid` Nexus file id, `fn` имя файла на Nexus, `url`, `auth`, флаги `on` (включён), `ex` (мод уже в сборке), `skip` (не переносить, дубль), `off` (мод сборки выключен выбором), `ei` индекс в активациях сборки, `f` файлы, `add` строки про дополнения для показа, `aj` исходный JSON дополнений, `pri` приоритет MO2 |
| `E` | ребро порядка: `from` проигравший мод, `to` победитель, `fi` индекс файла в `from`, `done` (учтено в сортировке), `cut` (разрезано на цикле) |
| `X` | пара конфликтующих файлов "сборка против входящего": `em`, `vm` индексы модов, `ef`, `vf` индексы файлов |
| `D` | дубль: `e` мод сборки, `v` входящий, `n` число общих файлов, `same` (все совпали), `lock` (ядро, выбора нет), `c` выбор (1 оставить сборку, 2 взять входящий), `c0` выбор по политике |
| `Q` | ошибка компиляции: `p` путь скрипта относительно `r6\scripts\` (нижний регистр), `k` ключ `путь:строка КОД`, `s` текст |
| `A` | пара архивов, перекрывающих ресурсы: `e`, `v` моды, `n` число общих хэшей ресурсов, `ea`, `va` имена архивов, `c`, `c0` (1 сборка, 2 входящий, 3 оба) |
| `MI` | прочитанный экземпляр MO2: `dir`, `mods`, `over` (overwrite), `pd` папка профиля, `prof`, `game`, `l` список (имя, префикс) из modlist.txt, `ord` (включён свой порядок архивов), `saves` (профильные сейвы есть), `ui` (профильный UserSettings.json) |

Глобальные: `mo2` (режим источника), `jo` (канал событий), `jbk`/`jbd` (пути для `done`), `dec`/`du` (решения и признак использования), `svc` (служебные имена лаунчера, `_*.json` и каталоги из списка; файлы с такими именами внутри мода не деплоятся), `nhid`/`nfold`/`njunk` (счётчики для события `mo2`).

### Функции

| Функция | Назначение |
|---|---|
| `srn`, `pf` | подмена "Vortex" на "MO2" в тексте; вывод с подменой |
| `W`, `U`, `lc`, `disp`, `ends`, `exists`, `lp` | преобразования строк и путей |
| `crc32c_sw`, `sse42`, `fcrc` | crc32c файла |
| `fid`, `samef` | идентичность файла по тому и индексу (`GetFileInformationByHandle`); проверка, что жёсткая ссылка указывает на оригинал |
| `sha256` | SHA-256 файла, шестнадцатеричная строка |
| `slurp`, `spit`, `mkdirs`, `rmtree` | ввод-вывод. `rmtree` не заходит в ссылки |
| `running` | процесс с таким именем запущен (Toolhelp) |
| `js`, `js8`, `pj`, `dump`, `dumps` | JSON |
| `ev`, `ph`, `prog`, `wn` | события: произвольное, начало фазы, прогресс (не чаще раза в 100 мс, последний шаг всегда), предупреждение (в stderr и событие) |
| `dget` | решение из `--decisions` по id; неподходящее значение даёт предупреждение и возврат к политике |
| `dllver` | версия DLL из ресурса (`major.minor.build`) |
| `walk` | рекурсивный обход мода в список `F`. Ссылки (reparse point) собираются отдельно и пропускаются. Для модов сборки (`ex=true`) пропускает служебные имена из `svc` |
| `nm` | разбор имени папки мода: имя, Nexus id, версия, дата. Три формы: Vortex `имя-id-версия-unixtime`, "свободная" `имя v1.2 4591 2.92 2026-10-25T...`, имя с версией в конце |
| `vcmp`, `newer` | сравнение версий по числовым сегментам; если версий нет, сравнение дат |
| `hs`, `vd` | размер и версия с датой для показа |
| `order` | топологический порядок модов (см. выше) |
| `pick` | интерактивный вопрос в консоли. С `--json` запрещён |

Подробности некоторых функций:

* `qv` снимает кавычки, раскрывает `\\`, `\n`, `\t`, `\r`, `\xNNNN` (до 4 hex-цифр), затем, если значение имеет вид `@ByteArray(...)`, превращает байты в UTF-8. Обрабатывает три варианта: Qt 5 (`\xd0\x98` дают байты), Qt 6 (двойное кодирование UTF-8, символы 0x80-0xFF) и случай, когда внутри уже настоящие символы больше 0xFF (возвращаются как есть).
* `qini` приводит имена секций и ключей к нижнему регистру, декодирует `%XX` в именах, секцию `General` называет `general`, строки с `;` пропускает, BOM снимает. Ключ в результате это `секция/ключ`; для массивов Qt ключ вида `installedfiles/1\modid`.
* `mmeta`: Nexus id берётся, только если `gameName` пуст или `cyberpunk2077` и `repository` пуст или `nexus`. Имя `installationFile` прогоняется через `nm()`: если из него вышел тот же Nexus id и дата, то версия и дата берутся из имени файла (версия в `meta.ini` бывает вида `1.2.0.0`, имя файла точнее). Файл Nexus (`fileid`) берётся из массива `installedFiles` для того же modid.
* `mver`: срезает префикс схемы версий MO2 (`f`, `n`, `d`) и ведущее `v`, убирает хвостовые `.0`, пока сегментов больше двух. Версия не интерпретируется, только чистится.
* `miread`: ищет экземпляр. Если `ModOrganizer.ini` нет по заданному пути, а задан короткий путь, пробует `%LOCALAPPDATA%\ModOrganizer\<имя>`. Ключи `[Settings]` `base_directory`, `mod_directory`, `overwrite_directory`, `profiles_directory` с подстановкой `%BASE_DIR%`; относительный путь без `%BASE_DIR%` считается от base. `gameName` обязан быть `Cyberpunk 2077`. Профиль: `--profile`, иначе `selected_profile`, иначе `Default`. Если modlist.txt в профиле нет, ошибка со списком профилей, где он есть.

Заметки по логике, которые нельзя увидеть из кода сразу:

* Если мод сборки и входящий мод это один мод (по `nid` или имени), а выбор "взять входящий", мод сборки не удаляется, а выключается (`off`). Его дополнения (`addons[]`), которые только добавляют файлы, переносятся в новый мод (`addedFiles`). Дополнение, которое заменяет файлы мода, не переносится, выводится предупреждение.
* При слиянии во все остальные профили добавляются входящие моды выключенными, а активным становится новый профиль `<прежний> + Vortex` (или `+ MO2`, с номером при повторе). Прежний профиль не трогается.
* `categoryOrder` в `_build_meta.json` получает новую категорию в конец.
* Архивы сравниваются только прямые потомки `archive\pc\mod\` (`lambda arc`), архивы REDmod и `archive\pc\patch` ядро не смотрит.
* Победитель по ресурсу архива определяется как раньше по имени: `wcscmp` по имени файла без каталога, регистр учитывается.

### Очистка и откат

`purge` читает манифест Vortex. Файл Vortex в игре считается своим, только если это жёсткая ссылка на файл staging (совпадают том и индекс файла). Такие файлы уезжают в карантин (`vtx\`). Если рядом лежит `<файл>.vortex_backup` (оригинал, подменённый модом), в игре остаётся текущая копия, а `.vortex_backup` уезжает в карантин. Файлы, которые после деплоя изменились (патч игры), не трогаются. Метки `__folder_managed_by_vortex` уезжают в `mk\`. Битые симлинки удаляются. Всё пишется в `purge.log`. Обратно: `robocopy "<карантин>\vtx" "<игра>" /e /move` и то же для `mk`. Нужны закрытыми Vortex, игра и ExLauncher.

`undo` ищет в `<ExMods>\_vtx2exl.backup` каталоги по шаблону `<сборка>-<8 цифр>-<6 цифр>[-N]` с файлом `_vtx2exl.json`, берёт последний по имени.

### Самопроверка

`selftest()` не обращается к диску игры. Проверяет: crc32c (программный и аппаратный, цепочки и хвосты), разбор и печать JSON (экраны, суррогаты, UTF-16), построение события, `dget`, `nm` на трёх формах имён, `vcmp`, `order` (простой порядок, цикл, цикл с модами сборки), `qv` (Qt 5, Qt 6, кавычки), `mlist`, `mver`, `mfilt`.

### Правка мода из карты (ExFix)

На экране карты у проблемы могут быть исправления "включить" и "выключить" мод. Для MO2 они отключены: профиль только читается. Для сборки выполняет `exfix()` в `ui/sys.js`:

1. Если запущена игра, отказ.
2. Если ExLauncher закрыт: UI сам правит `_activation_state.json` и в `_profiles.json` активный профиль. Правится только значение `enabled` у одной записи, остальной текст файла остаётся байт в байт (`tree` разбирает JSON с позициями). Перед этим копия в `_vtx2exl.backup\ui-fixes\<метка>`, запись через временный файл, перепроверка, откат при расхождении.
3. Если ExLauncher открыт: работа идёт через внешний патч лаунчера ExFix, которого в этом репозитории нет. UI ждёт, что рядом с ExMods есть папка `_exfix\cmd`, куда он кладёт файл `<id>.json` с командой, а патч в ответ кладёт `<id>.result.json`. Команды: `{op:'ping'}` (ожидается `data.build` с именем открытой сборки) и `{op:'set-enabled', cat, folder, enabled}` (ожидается `ok` и `data.changed`; статусы вида `profile-*` значат "сборка изменена, профиль не сохранён"). Ответ перекладывается в `cmd\done\`. Если команду никто не взял за отведённое время, UI забирает её назад (`no-answer`).
4. Если открыт лаунчер, а папки `_exfix\cmd` нет, либо лаунчер не отвечает на ping, UI отказывается и просит закрыть лаунчер. Вывод: без ExFix карта работает полностью, но чинить моды при открытом лаунчере нельзя.

Тесты на всё это в `ui/sys.test.js`, лаунчер подменён файловым "ответчиком".

### Конвейер `run()`

Фазы (подписи прогресса в UI те же):

1. Определить версию игры по ресурсу `Cyberpunk2077.exe` (`pe`), дату патча по mtime exe.
2. "Индекс игры": `vanilla()` читает индексы всех ванильных архивов из `archive\pc\content` и `archive\pc\ep1`, складывает хэши путей, размеры и контрольные суммы в `vanilla.bin` (ключ sha1 от списка файлов с размерами и mtime).
3. "Снимок игры": `fingerprint()` записывает `fp-<версия>-<дата>.bin.gz` (хэш, размер, контрольная сумма каждого ванильного ресурса) и сравнивает с самым свежим другим `fp-*.bin.gz`. Результат: множество `changed` ресурсов, изменённых патчем. Без прошлого снимка `changed` нет, и проверка "устаревшая замена" опирается на даты модов.
4. "Словарь путей": `names()` разворачивает `paths.data.mjs` в карту хэш -> путь. Хэши, которых в словаре нет, показываются как `0x...`; часть имён добавляется из ссылок внутри архивов модов.
5. "Чтение списка файлов": список модов и их файлов (`loadMods` или `loadMo2`), включённые моды, итоговая карта `dep`: путь -> список (мод, файл), последний побеждает.
6. "Индекс архивов": индекс каждого `archive\pc\mod\*.archive` и `mods\<redmod>\archives\*.archive` (кэш `arc\*.json` по размеру и mtime). Порядок загрузки: сначала не REDmod, по имени файла (Ordinal), потом REDmod. Побеждает первый.
7. "Индекс выключенных модов": нужен, чтобы подсказать "в выключенном моде есть недостающее".
8. "Распаковка заголовков", "Разбор заголовков", "Распаковка мешей", "Разбор мешей", "Распаковка внешностей", "Разбор внешностей": для архивов, которых нет в кэше, распаковываются заголовки CR2W (класс ресурса и список импортов), пакеты данных мешей (ссылки на материалы), `appearance`-ресурсы. Распаковка в C#-помощнике (`oo2ext_7_win64.dll`, `OodleLZ_Decompress`).
9. "Файлы ArchiveXL", "Твики", "Скрипты CET", "Скрипты redscript": разбор текстовых файлов (кэш `files.json`, версия схемы `PV`).
10. Проверки (таблица ниже).
11. Сборка графа: `mods`, `systems` (список из `SYSTEMS`), `edges` (мод -> система с весом), `issues`, отсортированные по тяжести, уверенности, числу ресурсов. Запись кэшей.

### Проверки

Поле `kind` у проблемы, уровень `sev` (порядок `SEV`: `crash`, `broken`, `risk`, `override`, `cosmetic`, `info`) и `conf` (оценка уверенности 0..1; это эвристика автора, не вероятность). У каждой проблемы: `title`, `explain`, `mods`, `winner`, `res` (первые 100 ресурсов), `fix` (действия `disable`, `enable`, `update`, `none`).

| kind | Что означает | Как определяется | Надёжность |
|---|---|---|---|
| `archive-overlap` | Два мода кладут один и тот же ресурс (по хэшу пути) в разные архивы. Побеждает архив, который раньше по имени. Также используется для перекрытия обычных файлов (не архивов) в общем разделе "файлы" | Таблица `prov`: хэш ресурса -> список архивов. `conf` 0.95; 0.6, если победитель зависит от регистра имён | Высокая для самого факта перекрытия. Вывод "что сломается" зависит от типа ресурса, а он грубый (текстуры = `cosmetic`, формы = `risk`, остальное `override`) |
| `identical-copy` | Одинаковые ресурсы (совпали размер, сжатый размер, число сегментов и sha1 сжатого основного сегмента) или файлы в двух модах, не конфликт | Сравнение в `same()` и побайтово для файлов | Высокая |
| `intended-override` | Один мод заменяет другой намеренно: перевод, патч, "заглушки" (архив на `z`, победитель в два раза больше), связанные моды | Эвристики `related()`, `isTr()`, `isPt()` по именам и Nexus id | Средняя: ошибается там, где имена не похожи |
| `dangling-ref` | Файлы мода ссылаются на ресурсы, которых нет ни в игре, ни во включённых модах | Импорты CR2W, ссылки внутри мешей, пакеты внешностей против `provided()` | Средняя. Известны остаточные ложные срабатывания на `.app` с неиспользуемыми ветками и материалами вне `chunkMaterials`. Важность считает `MSEV` (иконки `cosmetic`, остальное `broken`/`risk`) |
| `stale-replacer` | Мод подменяет ванильный файл, собран до патча, и этот файл изменён патчем | Дата ресурса или мода меньше даты патча, плюс множество `changed` из снимка. Группы: звуковые контейнеры, интерфейс, `.app`/`.ent`, руки и тело, сцены, морфы, толпа, `options.json` (`frag()`) | Хорошая со снимком, слабая без него (только даты). Группы и их тяжесть подобраны вручную |
| `xl-sector` | Правка секторов мира через ArchiveXL (`.xl`) не подходит к игре: сектор или блок не существует, число объектов не совпадает с ожидаемым (`expectedNodes`), мод старше патча и подменяет сектор файлом другого мода | Читается `.xl`, число узлов сектора берётся из ванильного архива или архива мода (`sectorNodes`) | Не-существование и несовпадение числа узлов: высокая. Уровень `crash` это эвристика (по логам ArchiveXL такие правки в основном пропускаются): `conf` 0.6-0.7 |
| `xl-overlap` | Несколько модов правят один сектор | Пересечение индексов `nodeDeletions` и наличие мутаций | Средняя |
| `tweak-invalid` | Файл `.xl` или твиков (YAML) не читается | Самодельный разбор YAML | Зависит от разборщика. Он знает подмножество YAML, которое встречается у модов; редкий синтаксис может дать ложную ошибку |
| `tweak-overlap` | Два мода задают одно поле TweakDB по-разному | Поля из YAML и из `TweakDB:SetFlat` в Lua; операции слияния (`!append` и т. п.) не считаются | Средняя; для Lua 0.6 |
| `lua-override` | Несколько модов CET подменяют один и тот же метод через `Override` | Разбор Lua регулярками | Средняя |
| `reds-replace` | Несколько модов заменяют одну функцию через `@replaceMethod` / `@replaceGlobal` | Регулярки по `.reds` без комментариев | Средняя. `@wrapMethod` не считается конфликтом |
| `reds-compile` | Скрипты не компилируются | Настоящая компиляция `scc_lib` на копии дерева скриптов с кэшем `final.redscripts` из игры. `crash`, если не компилируется весь набор | Высокая, если кэш и scc_lib одной версии |
| `missing-dep` | Нет фреймворка (ArchiveXL, TweakXL, redscript, CET, RED4ext) или модуля скриптов, который импортирует мод | Массив `FW` в `check.mjs` рядом с этой проверкой; импорты `.reds`, если компиляция не запускалась | Высокая для фреймворков по наличию файла, средняя для импортов |
| `dll-stale` | Нативный плагин (RED4ext, `.asi`) собран до патча | Метка времени в заголовке PE; если не похожа на настоящую, дата мода. Для плагинов `red4ext\plugins\` берутся только DLL с экспортом `Query` или `Main`; `.asi` и `RED4ext.dll` без этого условия | Средняя. Плагин мог остаться совместимым |

Вид файлового перекрытия (когда два мода кладут файл с одним путём вне архивов) выбирает `LK()` по пути: `.xl` даёт `xl-overlap`, `r6\tweaks` даёт `tweak-overlap`, `.reds` даёт `reds-replace`, `bin\x64\plugins` даёт `lua-override`, остальное `archive-overlap`. Побайтово одинаковые файлы дают `identical-copy`, отличающиеся только пробелами и строковыми литералами (Lua, `.reds`, YAML) дают `intended-override`.

Чего анализатор не делает: не смотрит `r6\config`, кроме `options.json`; не проверяет совместимость версий RED4ext-плагина и игры по таблице; не знает про зависимости модов друг от друга кроме импортов redscript; не читает `.archive` REDmod после `redMod.exe deploy`.

### Дублирование логики

Эти места реализованы дважды (ядро на C++ и анализатор на JS). При правке одного сверяй второе.

| Что | Ядро | Анализатор | Различие |
|---|---|---|---|
| ini Qt | `qv`, `qini` | `val`, `ini` в `mo2.mjs` | ядро переводит ключи в нижний регистр, JS нет |
| modlist.txt | `mlist` | цикл в `loadMo2` | JS ещё фильтрует каталоги регулярками |
| каталоги модов MO2 | условия в цикле `ph("scan"` | `dirs` в `loadMo2` | ядро пропускает каталоги с атрибутом "скрытый", JS каталоги, начинающиеся с точки |
| файлы мода MO2 | `mfilt` | `skipM`, `skipO` и разворот `root\` в `loadMo2` | при двух файлах с одним путём (с `root\` и без) оба берут файл без `root\` |
| индекс RDAR | `rdar` (только хэши) | `idx` (полный индекс) | форматы одинаковые, проверки размеров только в ядре |
| дерево скриптов для scc | лямбда `cc` в `run()` | `scc()` | JS кроме `r6\scripts` и `red4ext\plugins` берёт `mods\<m>\scripts` |
| Nexus id и версия из имён | `nm`, `mmeta` | регулярка по `installationFile` в `loadMo2`, `modDate` | |

## Вьюхи

`proto/whales/Whales.mjs`: анимация китов, компонент `<Whales width height paused />`, движок `engine()`. Рендер адаптирован из ascii-sharks (MIT), см. `proto/whales/LICENSE-ascii-sharks.txt`. Отключить анимацию: `VTX2EXL_NO_ANIM=1` (тесты ставят).
