# Сопровождение

## Что нужно

* Windows 10 или 11, x64.
* Visual Studio 2022 с компонентом C++ (нужны `ml64` и `cl`; `src\build.bat` находит их через `vswhere` и `vcvars64.bat`).
* Bun 1.3.14 (CI ставит именно эту версию, baseline-сборку). Baseline нужен, чтобы exe с встроенным рантаймом шёл на процессорах без AVX2.
* Node.js для `analyzer/test.mjs` и `tests/mo2.mjs`. Версия в CI не закреплена, берётся из образа `windows-latest`.
* Git. `gh` нужен только для ручной работы с релизами.
* Для анализатора на реальной сборке: `csc.exe` из .NET Framework 4 (`%WINDIR%\Microsoft.NET\Framework64\v4.0.30319`) и `bin\x64\oo2ext_7_win64.dll` из папки игры.

## Сборка

Только ядро:

```
src\build.bat
```

Собирает `src\crc32c.obj` (MASM) и `src\vtx2exl.exe` (`cl /std:c++20 /O2 /EHsc /W4 /utf-8`).

Всё вместе:

```
ui\build.cmd
```

Скрипт делает по порядку:

1. Если в корне нет `vtx2exl.exe`, собирает ядро и копирует `src\vtx2exl.exe` в корень. Если файл есть, ядро не пересобирается.
2. Если нет `ui\node_modules\ink`, выполняет `bun install`.
3. Удаляет старый `VTX2EXL-UI.exe`. Если не удалился (запущен), останавливается с сообщением "locked".
4. Запускает `bun build.mjs` с низким приоритетом. `ui/build.mjs` вызывает `Bun.build` в режиме `compile`, минификация включена, `react-devtools-core` подменён заглушкой, `../vtx2exl.exe` встроен через `import ... with {type: 'file'}` (см. начало `ui/sys.js`). Версия в ресурсе exe зашита как `1.0.0.0` и с тегом релиза не связана.

После правки `src/vtx2exl.cpp`:

```
src\build.bat
copy /y src\vtx2exl.exe .
ui\build.cmd
```

Либо удали корневой `vtx2exl.exe` и запусти `ui\build.cmd`. Без этого UI запакует старое ядро. Из Git Bash вызывай `cmd /c "<полный путь>\ui\build.cmd"`, с относительным путём он не находит себя.

Зависимости: `bun install` в `ui` и в `proto` (оба с `bun.lock`, CI ставит их с `--frozen-lockfile`). Интерфейс без сборки exe: `bun ui/main.jsx` (корневой `vtx2exl.exe` при этом должен существовать, он подключается как встроенный файл). `analyzer/` и `tests/` своих зависимостей не имеют. Для тестов вьюх понадобится ещё `bun install` в `proto/graph` и `proto/whales`.

Exe получается около 100 МБ (рантайм Bun внутри). `*.exe` и `*.obj` в git не лежат. Файлы `*.prev.exe` в корне скриптами не создаются.

## CI и релиз

Шаг `proof` запускает `.github/proof.mjs` и складывает в релиз txt-файлы: суммы по 10 алгоритмам, `BUILD-INFO`, `SOURCE-TREE`, `SOURCE-SCAN`, `PE-REPORT`, зависимости и их лицензии, скан Defender, `REPRODUCE`, инструкцию `VERIFY`. Шаг `rebuild` собирает проект второй раз в чистом клоне, чтобы сравнить байты (`/Brepro` в `src/build.bat` убирает метку времени из ядра). Сборка падает, если ядро слинковано с сетевой библиотекой. На `main` дополнительно ставится подпись `actions/attest-build-provenance`, проверка: `gh attestation verify <файл> --repo <репозиторий>`. Версии actions закреплены по хэшу коммита.

`.github/workflows/build.yml`. Запуск на каждый push (кроме правок только `*.md` и `LICENSE*`). Предыдущий незавершённый запуск той же ветки отменяется. Раннер `windows-latest`.

1. `actions/checkout`, `oven-sh/setup-bun` с адресом baseline-сборки Bun 1.3.14.
2. `bun install --frozen-lockfile` в `ui` и `proto`.
3. `ui\build.cmd` (с нуля собирает ядро, затем exe интерфейса).
4. Тесты (список выше).
5. `sha256sum VTX2EXL-UI.exe vtx2exl.exe > SHA256SUMS.txt`.
6. `upload-artifact` с именем `vtx2exl` (два exe и суммы).
7. Только на ветке `main`: удаляются все существующие черновики релизов (`select(.draft)`), создаётся новый черновик `v1.0.<номер запуска>` с тремя файлами, `--generate-notes` и кратким описанием. Тег создаётся на коммите при публикации.

Публикует релиз человек, руками на GitHub: проверить черновик, поправить текст, нажать Publish. Версия `1.0.N` это номер запуска workflow, а не семантическая версия. Два exe без цифровой подписи, SmartScreen при первом запуске предупредит (сказано и в README). Если нужен другой Bun, меняй адрес в `bun-download-url`.

Перед выпуском проверь на чистой машине (или чистой папке): `VTX2EXL-UI.exe --smoke` возвращает 0, в UI открывается "Самопроверка" и проходит.

## После патча игры

Что завязано на версию игры: ванильные архивы (`archive\pc\content`, `archive\pc\ep1`), снимок игры, словарь путей, кэш скриптов `r6\cache\final.redscripts` и совместимый с ним `scc_lib.dll`, версии фреймворков внутри самой сборки.

1. Про снимок. Анализатор различает "ресурс изменён патчем" по снимку `fp-<версия>-<дата>.bin.gz` в кэше. Снимок создаётся при первом запуске анализа на данной версии игры. Поэтому **до** обновления игры один раз прогони карту конфликтов (или `node analyzer/index.mjs --game <игра> --build <сборка> --quiet`), чтобы снимок старой версии лежал в кэше. Не чисть кэш (`%LOCALAPPDATA%\vtx2exl\cache`). Если снимка нет, анализатор скажет "нет снимка прошлой версии игры" и проверка `stale-replacer` пойдёт только по датам модов (слабее).
2. После патча прогони карту. Проверь вывод CLI: "Сравнение с прошлой версией игры: изменено N, добавлено N, удалено N". Сравнение идёт с самым свежим по mtime другим `fp-*.bin.gz`; если ты прогоняешь анализ на старой версии после новой, получится сравнение в обратную сторону.
3. Новые каталоги ванильных архивов. `vanilla()` в `analyzer/rdar.mjs` читает только `content` и `ep1`. Если CDPR добавит папку (новое дополнение), допиши в массив `['content', 'ep1']`. Признак проблемы: много `dangling-ref` на файлы, которые "должны быть в игре", и лишние `stale-replacer`.
4. Скрипты. Старый `redscript` (`scc_lib.dll`) обычно не читает кэш скриптов новой версии. Признак: в пробном прогоне "сборка и без вортекса не компилируется" и в анализаторе `reds-compile` у всей сборки. Это не баг переноса. Обнови в самой сборке (как моды, через лаунчер) redscript, RED4ext, ArchiveXL, TweakXL, Codeware, Cyber Engine Tweaks и зависимые моды, потом повтори. Эти пять-шесть проектов ядро не обновляет.
5. Если появился новый фреймворк, который нельзя подменять версией из Vortex или MO2, добавь его имя в регулярку `core` в `run()` (`red4ext|cyber engine tweaks|...`) и в массив `FW` в `analyzer/check.mjs` (рядом с проверкой `missing-dep`).
6. Словарь путей. Новые ванильные пути, которых нет в `analyzer/paths.data.mjs`, показываются как `0x...`. Обновление:
   1. Возьми `WolvenKit.Common.dll` из свежей установки WolvenKit (в нём лежат сжатые списки путей).
   2. `node analyzer/mkdict.mjs <путь\к\WolvenKit.Common.dll> <игра> [кэш]`. Скрипт ищет в DLL блоки `KARK`, распаковывает их Oodle-помощником, оставляет только пути, чьи FNV-хэши есть среди хэшей ванильных архивов, и пишет `analyzer/paths.br` (brotli). Вывод: число путей из числа ванильных хэшей.
   3. `analyzer/paths.data.mjs` должен остаться в виде `export default '<base64>';` и одной строкой. Преобразование из `paths.br` скриптом не делается, делай так:
      `node -e "const fs=require('fs');fs.writeFileSync('analyzer/paths.data.mjs','export default \''+fs.readFileSync('analyzer/paths.br').toString('base64')+'\';\n')"`
   4. `paths.br` в git не коммить (в репозитории его нет), удали после преобразования.
   5. Прогони `node analyzer/test.mjs`. Файл данных остаётся под GPL-3.0 (см. "Лицензии").
7. Oodle. Помощник загружает `oo2ext_7_win64.dll` и вызывает `OodleLZ_Decompress` с зашитой сигнатурой (14 параметров). Если игра сменила версию Oodle (имя DLL, число параметров), будет `нет распаковщика (csc.exe или oo2ext_7_win64.dll)` или `распаковщик: ...`. Исправляй строку `OO` в `analyzer/rdar.mjs` и имя файла в `check.mjs`, `mkdict.mjs` (`dll`). Имя exe помощника зависит от хэша исходника, пересоберётся сам.
8. Форматы. RDAR: сигнатура `RDAR`, заголовок 40 байт, размеры индекса. CR2W: сигнатура и смещения заголовка. Если анализатор после патча внезапно не находит ни одного перекрытия архивов, или `rdar()` в ядре не видит конфликтов архивов, первым делом проверь сигнатуры (раздел "Индекс RDAR" в `FORMATS.md`). Сбой там молчаливый.
9. Эвристики. `frag()` (группы `stale-replacer`), `PSYS`, `CSYS`, `KSYS` (системы), `MSEV` (тяжесть `dangling-ref`) подобраны вручную на версии 2.x. После крупного патча просмотри первые 30 проблем карты вручную на реальной сборке и поправь явные ложные срабатывания.
10. Версия игры и дата патча берутся из `bin\x64\Cyberpunk2077.exe` (ресурс версии и mtime). Если exe получил другой mtime без нового патча, появится лишний снимок с новым именем.
11. Прогони все тесты, затем `ui\build.cmd`.

## После обновления ExLauncher

Ядро пишет `_activation_state.json`, `_profiles.json`, `_build_meta.json`, `_category.json`, `_mod_meta.json`, `_mod_snapshot.json`, `_build_info.json` (форматы в `FORMATS.md`, раздел "Сборка ExLauncher"). Обновление лаунчера может поменять любой из них. Признаки: после переноса сборка не открывается или показывает пустую, моды не видны, активации пропали, лаунчер ругается на файлы, при запуске игры моды не деплоятся, обновления модов не находятся.

Как найти, что изменилось, не имея исходников лаунчера: сравнить файлы на диске до и после действия в самом лаунчере.

1. Сделай копию тестовой сборки (или создай новую пустую, это безопаснее): `robocopy <сборка> <копия> /e` либо просто новую сборку через интерфейс лаунчера.
2. Скопируй все json корня сборки и одной категории в каталог "до": `_build_info.json`, `_build_meta.json`, `_activation_state.json`, `_profiles.json`, `<категория>\_category.json`, `_mod_meta.json` и `_mod_snapshot.json` пары модов.
3. В лаунчере сделай одно действие: включи/выключи мод; поменяй порядок; создай категорию; создай разделитель; создай профиль; установи мод из папки и из архива; обнови мод. После каждого закрой лаунчер (он пишет при выходе).
4. Скопируй те же файлы в "после", сравни: `git diff --no-index до после` или `fc`. Сопоставь с таблицами в `FORMATS.md`: появились новые ключи, переименованы старые, изменился тип (строка/число), порядок, кодировка.
5. Перенеси в тестовую сборку что-нибудь маленькое и открой её в лаунчере:
   `vtx2exl <игра> <тестовая сборка> --apply --keep` (Vortex) или `vtx2exl --mo2 <экземпляр> <тестовая сборка> --apply`. Лаунчер должен показать моды, переключатели, порядок, разделители. Закрой лаунчер, сравни json с теми, что записал он сам.
6. Править надо место, где ядро формирует строки: в `run()` ищи `_mod_meta.json`, `_mod_snapshot.json`, `_category.json`, `_build_info.json`; состояния и профили собираются после `ph("write"`; чтение сборки в начале `run()` (`jn[3]`, `ea`, `byord`, `pmis`).
7. Если лаунчер перестал терпеть компактный json или BOM, это правится в `dumps` / `spit`. Ядро сейчас пишет UTF-8 без BOM.
8. Обнови `FORMATS.md` и `src/events.txt`, если менялось.
9. Особый случай: UI-часть "ExFix" (правка мода из карты при открытом лаунчере) использует внешний патч лаунчера. Его нет в репозитории. Если лаунчер обновился и патч слетел, UI вернёт сообщение "ExLauncher открыт, но не ответил: в нём нет патча ExFix..." и будет править файлы только при закрытом лаунчере. Это штатно.

Известные особенности лаунчера, которые уже учтены: он перезаписывает json сборки при любом действии (поэтому ядро отказывается работать при запущенном лаунчере); не любит дубликаты имён в `modOrder` и `categoryOrder`; порядок архивов в `modlist.txt` пишет по имени; при обновлении мода с Nexus кладёт новую папку в конец массива активаций, оставляя старый `order` (поэтому ядро сравнивает профиль и состояние после сортировки по `order`).

## После изменений в Vortex или MO2

Vortex. Читается только `vortex.deployment.json` и staging. Что делать:

1. Выполни Deploy в новом Vortex и сравни манифест с таблицей в `FORMATS.md`. Ломается обычно на ключах (`stagingPath`, `files`, `relPath`, `source`, `target`) или на способе деплоя.
2. Если `target` стал непустым, у Vortex появилась раскладка, которую ядро не знает; что именно она означает, в коде не выяснялось. Ядро намеренно останавливается. Научить его значит менять составление путей (`win`, `dep` в начале `ph("read"`).
3. Если staging переименовывает папки модов иначе, смотри `nm()` и тест `dir name` в `selftest()`.
4. Для очистки: Vortex перестал ставить метку `__folder_managed_by_vortex` или `.vortex_backup`: правь `scan()` и `purge()`.

MO2. Не проверялось на реальной установке, поэтому первым делом сделай такую проверку (на копии):

1. `vtx2exl --mo2 <экземпляр> <новая тестовая сборка>` без `--apply`. Прочитай события: `mo2` (число модов, включено, выключено, разделителей, файлов overwrite) должно совпасть с тем, что показывает MO2. `verify.diff` и `verify.lost` обязаны быть нулём.
2. Сверь порядок: в интерфейсе MO2 самый нижний мод в левой панели побеждает, он должен оказаться последним в итоговом порядке (`порядок, последний побеждает` в stderr).
3. Если MO2 изменит формат `modlist.txt` или `meta.ini`, правь парные функции в ядре и анализаторе (таблица "Дублирование логики" в `ARCHITECTURE.md`) и добавь случай в `tests/mo2.mjs`.
4. Проверь глобальное расположение экземпляров: UI ищет их в `%LOCALAPPDATA%\ModOrganizer\*` (`MO` в `ui/sys.js`). Если MO2 хранит их в другом месте, поправь эту константу.

## Новый источник (другой менеджер модов)

Образец: MO2. Ядро устроено так, что всё, что не зависит от источника (поиск дублей, конфликты файлов и архивов, политика и решения, компиляция скриптов, копирование, запись сборки, откат), общее. От источника нужны только входные данные. Чтобы увидеть все точки ветвления, выполни `grep -n mo2 src/vtx2exl.cpp` (около 30 мест).

### Что должен дать источник

1. Папка модов: каждый подкаталог это мод, корень мода соответствует корню игры (если нет, сделай развёртку, как `root\` у MO2 через `mfilt`).
2. Какие моды включены (`dep`: множество `lid` = имя папки в нижнем регистре).
3. Порядок или явный победитель на каждый файл:
   * Vortex отдаёт победителя по каждому файлу (`win` из манифеста), приоритетов у него нет;
   * MO2 отдаёт приоритет мода (`pri`; больше значит побеждает), победитель вычисляется (`win[f.key] = ms[i].lid` в цикле после сортировки по `pri`).
4. Метаданные мода, если есть: Nexus id, версия, дата, `fileId`, имя файла, автор, ссылка (`M::nid`, `ver`, `date`, `fid`, `fn`, `auth`, `url`, `desc`). Без них обновления в лаунчере работать не будут.
5. Дополнительные "моды": аналог Overwrite (синтетический мод с наивысшим приоритетом).
6. Разделители, если есть (`sps`), для `_category.json`.
7. Файловые фильтры: что в моде не относится к содержимому игры.

1. Глобальный флаг `mo2` и его установка в `wmain` (`mo2 = !inst.empty();`) заменить на перечисление источников или добавить второй флаг. Добавить ключ в разбор аргументов в `wmain` (по образцу `--mo2`) и ветку в проверку числа позиционных аргументов.

Интеграционный тест: скопируй `tests/mo2.mjs` как образец. Он строит каталог источника во временной папке (`put(...)`), запускает ядро с `--json` и проверяет события и файлы результата. Добавь строку в CI (`.github/workflows/build.yml`, шаг `test`).

## Новая проверка в анализаторе

1. Данные собери в `run()` в `analyzer/check.mjs`: после соответствующей фазы (см. таблицу фаз в `ARCHITECTURE.md`). Файлы мода и их абсолютные пути уже есть в `deployed` (последний победитель каждого пути) и в `mods[].files`. Разборы текстовых файлов оборачивай в `parsed(d, 'метка', fn)`, чтобы они попали в кэш `files.json`, и при смене структуры результата поднимай `PV`.
2. Создай проблему вызовом `add(kind, sev, sys, ms, title, explain, {res, winner, conf, fix, key})`. `kind` строка, `sev` одна из `crash | broken | risk | override | cosmetic | info`, `sys` система из `SYSTEMS`, `ms` затронутые моды (объекты), `res` список `{path, hash}` не более 100, `fix` массив `F('disable' | 'enable' | 'update' | 'none', мод, подпись)`. `conf` честно оценивай, UI показывает её процентами. `key` нужен, если в заголовке нет уникальной части (идентификатор проблемы = хэш от вида, модов и ключа).
3. Подпись для нового вида: `KR` в `proto/graph/Graph.mjs` (без неё покажется английский ключ). Если новая тяжесть, то `SEV`, `SR` и цвета (`SC` в `ui/map.jsx`, `SC` в `Graph.mjs`).
4. В UI выполняются только `disable` и `enable` (`fix` в `Board`, `ui/map.jsx`). `none` показывает подпись заметкой, `update` открывает диалог "Это делается вручную".
5. Тест: юнит на разбор в `analyzer/test.mjs`; сквозной случай в `analyzer/bench.mjs` (если у тебя есть сборка, на которой проблема воспроизводится). Не забудь контрольные примеры, где проверка должна молчать (блок контролей в конце `bench.mjs`).
6. Прогони карту на реальной сборке и посмотри на число срабатываний и первые тридцать. Проверка с шумом вредна: пользователь отключает рабочие моды.

## Новое JSON-событие

1. В ядре: `O("имя").s("поле", текст).n("число", n).b("флаг", ok).r("массив", готовый_json).go();` Строки идут через `srn()`, числа через `n`, готовый JSON-фрагмент через `r`.
2. Опиши событие в `src/events.txt`: поля и смысл. Если меняется смысл или тип существующего поля, увеличь версию в `O("start").n("v", 1)`. UI версию не проверяет, но человек, пишущий свой клиент, будет.
3. В UI: `feed()` в `ui/job.jsx` (новая ветка `case`); неизвестные события пишутся в журнал как `raw` и не ломают работу. Если событие нужно показать, добавь поле в состояние задачи (`useJob.start`) и компонент.
4. Проверь событие в `tests/mo2.mjs` (или в `selftest()`: там есть образец проверки `O(...).str()`), в `ui/app.test.jsx` добавь подставное событие.
5. Событие `done` должно оставаться последним. Все события пишутся и сбрасываются сразу, не буферизуй.

## Известные ограничения

* Только Windows: пути с `\\?\`, Win32 API, `tasklist`, `csc.exe`.
* Конфликты ресурсов архивов ядро ищет только среди `archive\pc\mod\*.archive`, сравнивая хэши путей, без сравнения содержимого. Архивы REDmod и `archive\pc\patch` не смотрит. Анализатор берёт ещё `mods\<m>\archives\*.archive` и сравнивает содержимое.
* Порядок архивов в игре принят как "первый по имени побеждает", имена сравниваются побайтно, с учётом регистра. Приоритеты Vortex и MO2 в порядок архивов не переносятся: лаунчер сортирует по имени. Для MO2 это означает, что победитель по ресурсу архива может отличаться от того, что было в MO2 (предупреждение выводится только при включённом `enforce_archive_load_order`).
* Категории MO2, заметки и рекомендации, `downloads\*.meta` не переносятся. Версия и Nexus id MO2 берутся из `meta.ini` и имени файла установки, у Vortex из бэкапа его базы.
* Выборы FOMOD есть только у Vortex. Моды, где лаунчер не повторит выбор, и все FOMOD-моды из MO2 заморожены от обновлений через `ignoreUpdatesUntil`. Снять заморозку можно в лаунчере, тогда выбор придётся проверить руками.
* MO2: переносится один выбранный профиль. Сейвы и `UserSettings.json` профиля не переносятся.
* Дубликат имени папки среди входящих модов из разных корней (`--extra` и основная папка) не проверяется явно, что получится при записи (склейка в одну папку или отказ при копировании), не проверено.
* Жёсткие ссылки: файл в сборке и в источнике это один и тот же файл на диске, пока источник и сборка на одном томе. Ядро проверяет совпадение после создания ссылки.
* Карта конфликтов для MO2 профиля только читает; исправление "включить/выключить" делается в MO2.
* Точность анализатора оценена вручную на небольшой выборке (порядка тридцати проблем, около 93 процентов до последних правок эвристик), строго не измерялась. Оценки `conf` это не вероятности.

## Что не проверено

Это надо учитывать, прежде чем доверять утверждению в других документах.

* Поддержка MO2 написана по исходникам MO2 и проверена только синтетическими каталогами и юнит-тестами. На настоящей установке MO2 ничего не запускалось. Сюда входят: чтение `ModOrganizer.ini`, `modlist.txt`, `meta.ini`, расположение глобальных экземпляров в `%LOCALAPPDATA%\ModOrganizer`, имя группы настроек плагина игры, относительные пути в `mod_directory`.
* Живое поведение ExLauncher с разделителями `__sep__<guid>`, которые пишет ядро для MO2, и с категорией, созданной ядром при слиянии. Тест `tests/mo2.mjs` проверяет только содержимое файлов.
* Версия ExLauncher, с которой сверены форматы, не записана. Все утверждения о поведении лаунчера (деплой, порядок, проверка обновлений, снимки, отказ при пропавших папках) относятся к его коду на момент сверки.
* Работа Vortex с деплоем не жёсткими ссылками (симлинки, копирование).
* Смысл порядка внутри `archive\pc\mod\modlist.txt` на стороне игры.
* Часовой пояс: `snapshotAt` пишется в UTC, лаунчер сравнивает с локальным временем. На практике безвредно, не проверялось в разных поясах.
* Лицензии npm-пакетов, вшитых в exe (ink, react, chalk и их зависимости): отдельным файлом они к релизу не прикладываются. Нужно ли это сделать, не решено.
* Работа интерфейса вживую на разных терминалах и шрифтах. Тесты проверяют ширину глифов и рендер через `ink-testing-library`, скриптовый сквозной прогон `ui/pty.mjs` ручной.
